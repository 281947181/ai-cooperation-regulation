## 1. 任务目标

实现 Acceptance Bridge V1，使完成开发并推送远程 Git 的 Codex 主代理能够在不需要用户复制粘贴的情况下：

1. 将规范化的 repository 映射到唯一、明确、经过一次性确认的 ChatGPT Project / AUTO-REVIEW 对话。
2. 通过 Codex 可用的受控浏览器能力把 `[CODEX_ACCEPTANCE_REQUEST]` 自动送达该固定对话。
3. 以 `review_id` 和请求摘要实现跨重试、跨进程的幂等控制，避免重复发送或错绑结果。
4. 等待、读取并严格解析 `[CODEX_ACCEPTANCE_RESULT]`，校验 Contract、repository、branch、commit 和 review_id 身份。
5. 将 PASS / REWORK / BLOCKED 返回 Codex 主代理并持久化；REWORK、BLOCKED 或 Bridge 失败均停止自动执行。
6. 使用本 Task Contract 自身完成第一次真实端到端验收。

本任务的目标是“无人复制”，不是“无人治理”。允许一次性目标绑定和必要的登录操作；禁止自动选择未知对话、自动修改权限或形成无人监管的返工循环。

## 2. 已确认设计结论

### 2.1 交付形式

Bridge 实现为用户级个人 Skill：

```text
~/.codex/skills/acceptance-bridge/
├── SKILL.md
├── agents/openai.yaml
├── scripts/bridge_state.py
└── references/protocol.md
```

Skill 负责工作流和浏览器编排；确定性状态、映射解析、摘要计算及结果校验放入脚本。不得把脆弱的幂等判断只写成自然语言提示词。

创建 Skill 时必须使用当前 `skill-creator` 的初始化、元数据生成和验证流程，不手工伪造不完整 Skill 结构。

### 2.2 私有运行数据

私有映射与状态放在：

```text
~/.codex/review-bridge/
├── targets.toml
└── state.sqlite
```

`targets.toml` 保存 repository 到 ChatGPT 验收目标的映射；`state.sqlite` 保存幂等和结果状态。两者不得加入任何 Git 仓库。

### 2.3 公开规约与私有配置边界

`ai-cooperation-regulation` 只保存通用协议、模板、Skill 调用规则和本项目自己的 PERSISTED Contract，不保存任何私人 ChatGPT conversation URL、Cookie、Token、会话文件或浏览器配置。

## 3. Repository 映射规范

Bridge 必须把以下等价 GitHub 地址规范化为同一个 repository key：

```text
https://github.com/OWNER/REPO.git
https://github.com/OWNER/REPO
git@github.com:OWNER/REPO.git
ssh://git@github.com/OWNER/REPO.git
```

本任务目标仓库的 canonical key 固定为：

```text
github:281947181/ai-cooperation-regulation
```

V1 不支持通过模糊仓库名匹配。无法规范化、同一 key 存在多个启用目标、或请求 repository 与映射 key 不一致时，必须停止并返回本地 Bridge 错误。

`targets.toml` 至少支持：

```toml
[targets."github:281947181/ai-cooperation-regulation"]
enabled = true
host = "https://chatgpt.com"
project_id = "<private-local-value>"
conversation_url = "<private-local-value>"
expected_project_title = "AI协作规约"
expected_conversation_title = "[AUTO-REVIEW] AI协作规约"
browser_surface = "in-app-browser"
response_timeout_seconds = 900
```

实际 `project_id` 和 `conversation_url` 是一次性运行参数，不属于需求变更，也不进入本 Contract Hash。Codex 不得猜测它们。若用户尚未提供目标，允许在实现阶段请求一次明确绑定；绑定完成后，日常验收不得再要求用户复制消息。

## 4. 一次性目标绑定

绑定过程必须：

1. 使用明确的 ChatGPT URL 或用户明确点选的现有浏览器标签页。
2. 验证 host 精确为 `https://chatgpt.com`。
3. 验证 Project ID、项目标题和对话标题均与待写入映射一致。
4. 如果目标对话不存在，可以在用户对“创建一个固定 AUTO-REVIEW 对话”进行动作时确认后创建；不得创建多个候选对话。
5. 在 `targets.toml` 写入确定性 URL/ID 后重新打开并验证一次。
6. 不读取或持久化 Cookie、Token、密码、浏览器历史或其他对话内容。

运行期必须直接使用已绑定 URL/ID，禁止每次搜索最近聊天、按相似标题猜测目标或静默切换浏览器。

## 5. Acceptance Request 生成

Bridge 只接受已完成以下前置条件的请求：

```text
最终 diff 已检查
最终验证已完成
commit 已创建
push 已成功
Remote main/目标分支已确认包含请求 commit
Task Contract 可恢复
```

Request 必须符合当前 `runtime.md`，至少包含：协议版本、完整 Contract 身份、review_id、repository、branch、40 位 commit、任务信息、主要修改、最终验证、Docker、PROJECT_BASELINE 和已知风险。

`review_id` 固定使用：

```text
<TaskContractID>/<RFC3986-percent-encoded-branch>/<40位小写GitSHA>
```

Bridge 必须对规范化 Request Envelope 计算 SHA-256 `request_digest`。同一 `review_id` 对应不同 `request_digest` 时属于身份冲突，禁止覆盖或重新发送。

## 6. 幂等状态存储

`state.sqlite` 至少包含一张以 `review_id` 为主键的记录表，保存：

```text
review_id
request_digest
task_contract_id
task_contract_version
task_contract_hash
repository_key
branch
commit_sha
target_key
status
attempt_count
sent_at
result_received_at
verdict
result_digest
last_error
created_at
updated_at
```

状态迁移至少包括：

```text
PREPARED
→ CLAIMED
→ SENT
→ DELIVERED
→ RESULT_RECEIVED
→ PASS | REWORK | BLOCKED
```

Bridge 失败状态包括：

```text
DELIVERY_FAILED
RESPONSE_TIMEOUT
INVALID_RESPONSE
IDENTITY_MISMATCH
TARGET_NOT_FOUND
```

数据库操作必须使用事务和唯一约束。并发进程只能有一个获得同一 `review_id` 的发送权。

重试规则：

- 已存在 PASS / REWORK / BLOCKED：直接返回已存结果，不再访问浏览器。
- 已存在相同 digest 的 SENT / DELIVERED：先到固定对话中查找该 review_id，不得直接重发。
- 已存在不同 digest：返回 IDENTITY_MISMATCH。
- DELIVERY_FAILED 可以有限重试，但总发送尝试不得超过 2 次；每次重试前必须先确认对话中不存在该 review_id。
- RESPONSE_TIMEOUT 不得自动重复发送原 Request；只允许继续结果回收。

## 7. 浏览器自动送达

使用当前 Codex/ChatGPT 提供的 Browser 能力，优先固定使用 `in-app-browser`。不得通过抓取 Cookie、复用未授权浏览器配置或模拟未知登录绕过认证。

发送前必须验证：

```text
当前 host
Project ID/标题
conversation URL/ID/标题
repository mapping
review_id 尚未在对话中出现，或出现时进入恢复流程
```

验证成功后才允许发送一次完整 Acceptance Request。发送后必须通过页面中实际渲染的用户消息确认相同 `review_id` 已出现，再记录 `DELIVERED`。仅点击发送按钮、DOM 调用返回或输入框变空不能视为送达成功。

浏览器未登录、目标不存在、页面身份不符、出现 CAPTCHA/权限确认或无法证明送达时，必须停止并返回明确 Bridge 状态；不得向其他对话发送。

本 Task Contract 明确授权：在已完成一次性绑定且后续 Task Contract 设置 `acceptance_bridge=required` 时，Codex 可以无需每轮人工复制或再次确认，将该轮 Acceptance Request 发送到映射中唯一的 AUTO-REVIEW 对话。该授权不包含创建新对话、切换目标、发送其他内容或处理 CAPTCHA。

## 8. 结果等待与回收

送达后在 `response_timeout_seconds` 内进行有界等待。每次等待不超过 60 秒，并定期重新读取对话状态。

只接受位于本次 Request 之后、来自 assistant、包含唯一 `[CODEX_ACCEPTANCE_RESULT]` Envelope 的响应。解析后必须校验：

```text
protocol_version
task_contract_id
task_contract_version
task_contract_hash
review_id
contract_resolution
commit_resolution
verdict
contract_checks
issues
next_action
```

以下任一情况不得接受为结果：

- 普通自然语言称“通过”，但没有有效 Envelope。
- review_id、Contract 身份、repository、branch 或 commit 不匹配。
- verdict 不属于 PASS / REWORK / BLOCKED。
- 响应位于本次 Request 之前。
- 同一 Request 后出现多个相互冲突的有效结果。

有效结果写入 SQLite，并计算 `result_digest`。主代理必须收到结构化结果和证据位置。

超时后记录 RESPONSE_TIMEOUT。下一次恢复运行应从固定对话继续查找结果，不得重发 Request。

## 9. Codex 主代理处理结果

```text
PASS
→ 输出验收通过，任务闭环完成。

REWORK
→ 输出返工项并停止；等待 ChatGPT/用户给出明确返工指令。

BLOCKED
→ 输出阻塞原因并停止。

Bridge 失败状态
→ 输出状态、证据和恢复命令；不宣称任务已验收。
```

V1 禁止收到 REWORK 后自动修改代码、自动生成新 Contract 或再次提交。Bridge 只能自动交付和回收验收，不能扩张 Codex 的开发授权。

## 10. Skill 触发与项目集成

`acceptance-bridge` Skill 的 description 必须覆盖：任务完成并 push 后自动提交 ChatGPT 验收、恢复待处理 review_id、查询 Bridge 状态三类触发。

公开 `runtime.md` 和任务模板应增加最小、非重复的调用约定：

```text
acceptance_bridge: required | optional | disabled
acceptance_target_key: <canonical repository key>
acceptance_response_timeout_seconds: <positive integer>
```

只有 `required` 才把 Bridge 成功取得有效 Result 作为任务闭环条件。`optional` 失败时可以回退人工交付但必须明确报告；`disabled` 不得自动发送。

如需修改 `~/.codex/AGENTS.md`，只能增加轻量 Bootstrap：正式实现任务在 push 后按 Task Contract 调用 `$acceptance-bridge`；不得复制完整协议或写入私人 target。

## 12. 禁止事项

禁止：

1. 把 conversation URL、Project ID、Cookie、Token、密码或浏览器会话信息提交到 Git。
2. 搜索最近聊天并猜测验收目标。
3. 向映射之外的对话发送消息。
4. 同一 review_id 重复发送。
5. 使用纯 JSONL 在无锁条件下承担并发幂等状态。
6. 修改现有 Luna/Terra Agent 配置，除非发现与本任务直接相关且先说明。
7. 创建写入型 Subagent 或允许 Subagent commit/push。
8. 自动处理 CAPTCHA、登录密码、OTP 或权限提升。
9. 将页面完整 DOM、其他聊天内容或浏览器历史写入日志。
10. 因 Bridge 失败而声称 Acceptance PASS。
11. 收到 REWORK 后自动修改并重试。
12. 实现 ChatGPT ↔ Codex 无限循环。
13. 为 Bridge 引入常驻后台服务、远程数据库或第三方 SaaS；V1 使用本地 Skill + SQLite。

## 14. 实现与验证顺序

1. 同步并阅读远程 `main` 的五个规约文件及本 Contract。
2. 核对当前 OpenAI Docs、本机 Browser/Skill 能力和实际目录。
3. 运行 `skill-creator` 初始化 `acceptance-bridge`，生成必要元数据和资源目录。
4. 先实现并测试 repository 规范化、SQLite 状态机、digest、parser 和恢复逻辑。
5. 再实现 Skill 浏览器送达/回收工作流。
6. 增量更新公开规约和模板，持久化本 Contract；不得复制整个 Skill 实现到规约正文。
7. 完成一次明确目标的一次性绑定。
8. 运行本地单元/集成测试，至少覆盖成功、重复、冲突、超时、无效响应和目标不匹配。
9. 使用 Luna 做只读能力核对，使用 Terra 做最终只读 Review。
10. 主代理检查最终 diff、隐私泄露、测试、配置加载和 Skill discovery。
11. commit、push，并确认远程 `main` 等于当前 HEAD。
12. 以本 Contract 和最终 commit 生成真实 Acceptance Request，通过新 Bridge 自动送达并回收结果。

## 16. 验收标准

只有以下全部满足才可 PASS：

```text
AC-01 PERSISTED Contract 可按 locator 从远程仓库精确恢复，Hash 匹配。

AC-04 targets.toml/state.sqlite 均为本地私有文件，Git 中无私人目标或凭据。
AC-05 SQLite 主键、事务和 digest 能阻止并发及重试重复发送。
AC-06 Browser 发送前完成全部身份校验，发送后以实际渲染消息确认送达。
AC-07 Result parser 严格校验协议、Contract、review_id 和 commit。
AC-08 PASS/REWORK/BLOCKED 及所有 Bridge 失败状态可正确持久化、恢复和返回。
AC-09 RESPONSE_TIMEOUT、进程中断和重复启动不会重发 Request。
AC-10 REWORK/BLOCKED 不触发自动改码或无限循环。

AC-12 公共 runtime/task/acceptance 模板与实际实现一致且不大量重复。
```

## 17. 完成与失败语义

实现、测试、commit 和 push 成功，但 T-15 未完成时，本任务只能报告“部分完成”或相应 Bridge 失败状态，不能报告整体完成。

如果尚未提供一次性目标绑定，允许先完成实现和离线测试，但最终状态必须为 BLOCKED / TARGET_NOT_FOUND，等待用户提供明确目标；不得以示例 URL 代替真实端到端验证。
